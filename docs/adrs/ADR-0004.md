# [ADR](<https://github.com/pszjmb1/llm-play/wiki/Architectural-Decision-Records-(ADRs)>)-0004: Edge Function Implementation for Submission Handling

## Context

As part of implementing the MVP Submission Handling feature (#14), we need to create a lightweight, secure mechanism to receive and process environment submissions. This mechanism needs to validate submission data, store it in the database, and queue jobs for processing.

The submission handling process is a critical component of the [Environment Lifecycle](./ADR-0002.md) that enables the "Creation & Submission" stage. Our implementation choices here will affect the platform's responsiveness, security, and developer experience.

## Decision

We will implement environment submission handling using **Next.js Edge API Routes** rather than dedicated Supabase Deno Edge Functions.

The implementation will include:

1. A dedicated Edge API Route at `/app/api/edge-submit/route.ts` with the `runtime: 'edge'` configuration
2. A client-side service (`EdgeSubmissionService`) to interact with this endpoint
3. Robust validation using existing validation functions
4. Direct interaction with Supabase tables via the edge-compatible client
5. Comprehensive error handling and response formatting

## Business Value

This approach delivers value by:

- **Performance**: Low-latency processing of submissions globally through edge network deployment
- **Developer Experience**: Consistent codebase using familiar patterns and tooling
- **Security**: Isolated execution environment with robust validation
- **Simplicity**: Reduced operational complexity by using the existing Next.js infrastructure
- **Cost Efficiency**: No additional infrastructure required beyond the current Next.js deployment

## Consequences

### Positive

- Faster development time by reusing existing code and patterns
- Consistent error handling across the application
- Simplified deployment and monitoring
- Reduced latency for users globally
- Easier debugging and tracing of issues

### Negative

- Limited runtime capabilities compared to full Node.js environment
- No direct access to certain Node.js APIs and packages
- Need for careful size optimization to maintain fast cold starts
- Some logic duplication with the standard API routes

### Neutral

- Will require refactoring if we later decide to move to a more separate architecture
- Functionality concentrated in the Next.js application rather than distributed among specialized services

## Alternatives Considered

1. **Supabase Deno Edge Functions**:

   - Pros: Better isolation, dedicated Deno runtime
   - Cons: Separate deployment process, duplicate validation logic, additional complexity
   - Rejected due to increased development overhead and complexity

2. **Standard Next.js API Routes**:

   - Pros: Full Node.js runtime, access to all libraries
   - Cons: Higher latency for global users, potentially slower cold starts
   - Rejected in favor of edge performance benefits

3. **Serverless Functions (AWS Lambda, etc.)**:

   - Pros: Potentially more powerful runtime, better scaling
   - Cons: Additional infrastructure, separate deployment pipeline
   - Rejected due to unnecessary complexity for our requirements

4. **Direct Client-to-Database Operations**:
   - Pros: Simpler architecture, faster development
   - Cons: Security risks, exposure of database structure
   - Rejected due to security concerns

## Effort Estimation

- **Time**: 1-2 weeks for implementation and testing
- **Resources**:
  - Backend developer (0.5 FTE)
  - Frontend developer (0.25 FTE)
  - QA engineer (0.25 FTE)
- **Complexity**: Medium
  - Integration with existing validation and database systems
  - Ensuring Edge compatibility
- **Dependencies**:
  - Existing validation logic
  - Supabase edge-compatible client
  - Database schema for environments and jobs
- **Risks**:
  - Edge runtime limitations
  - Cold start performance
  - Potential security vulnerabilities

## Status

Accepted
